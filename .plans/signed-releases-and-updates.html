Update validation: Apple signature only

security
Verified against Sparkle's validator source, not just the docs: a host with no EdDSA key accepts an app-bundle update whose code signature is valid and matches the host's. Both apps you showed lean on Apple's signature the same way.
pickNo SUPublicEDKey
  • Zero extra secrets; the p12 you already have is the whole chain.
  • Full zip every update (no deltas). Fine at mbl's size.
  • Tampered zip is rejected after extraction rather than before. Same outcome.
  • Can add a key in a later release without breaking the chain.
altGenerate an EdDSA pair
  • Unlocks delta updates and verify-before-extract.
  • One more secret in GitHub, and a key you must never lose.
use EdDSA

Where the appcast lives: latest-release asset

hosting · changed from earlier
I suggested GitHub Pages earlier. On reflection, GitHub gives a stable redirect URL for the newest release's assets, so the workflow can upload the appcast next to the zip and nothing needs committing back. Sparkle follows the redirect. Raising it now rather than building the heavier one.
pickgithub.com/…/releases/latest/download/appcast.xml
  • Feed lists one entry: the release it sits in.
  • No Pages branch, no bot commit, no extra permissions.
  • Pre-releases are excluded from "latest" automatically.
altGitHub Pages branch
  • Feed can carry release history and notes for several versions.
  • Workflow commits appcast.xml to a gh-pages branch each release.
host on Pages

Versioning: the git tag is the version

release process
Info.plist currently hardcodes 0.1 / build 1. Sparkle compares CFBundleVersion, so it must increase every release.
pickTag v1.2.3 sets both plist fields to 1.2.3
  • Workflow triggers on tags matching v*.
  • bundle.sh reads VOICE_VERSION, defaulting to 0.0.0-dev locally.
  • Sparkle's comparator handles dotted numerics; dev builds never out-rank a release.
altShort version from tag, build number from run count
  • Lets you re-release the same marketing version.
  • Two numbers to reason about instead of one.
separate build number

Local builds stay on Apple Development and never see the feed

dogfooding
An Apple Development build can never accept a Developer ID update; the identities differ and Sparkle would reject it. Rather than surface a confusing error, dev builds simply have no updater.
pickSUFeedURL only written for release builds
  • bundle.sh adds the feed key only when VOICE_RELEASE=1.
  • No feed means the update menu slot is hidden and Sparkle never starts.
  • To dogfood updates, run the released zip.
altBuild locally with Developer ID too
  • Your day-to-day build could take real updates.
  • Every local build would overwrite your privacy grants unless the identity is stable, and it invites shipping unnotarized builds by accident.
local Developer ID

C · Mechanical work

Files and the moving parts (trust me)
scripts/bundle.shEnv-driven version and identity. Copies Sparkle.framework from the SwiftPM bin path. Signs Sparkle's XPC services and Autoupdate binary, then the framework, then the app, with --options runtime --timestamp.
Voice.entitlementscom.apple.security.device.audio-input. Hardened runtime blocks the mic without it. No library-validation exemption is needed once Sparkle is re-signed by us.
Package.swiftSparkle 2.x dependency. Linker rpath @executable_path/../Frameworks via unsafeFlags, which is permitted for a root package.
.github/workflows/release.ymlTag trigger, keychain import, build, notarize, staple, zip, appcast, release upload. Notarization waits are typically a few minutes.
Sources/Voice/Updater.swiftWraps Sparkle. Exposes an enum state and a callback the app uses to render the menu item and icon badge. Sparkle's install-and-relaunch handles the swap.
Sources/Voice/App.swiftVersion item at top of makeMenu, updater slot below it, badge composited onto the status image in updateStatusIcon.
README.mdRelease section: how to tag, what the workflow produces, and that local builds do not self-update.

Appcast the workflow writes

<rss version="2.0" xmlns:sparkle="http://www.andymatuschak.org/xml-namespaces/sparkle">
  <channel>
    <title>mbl</title>
    <item>
      <title>0.2.0</title>
      <sparkle:version>0.2.0</sparkle:version>
      <sparkle:minimumSystemVersion>26.0</sparkle:minimumSystemVersion>
      <enclosure url="https://github.com/discorev/mbl-voice/releases/download/v0.2.0/Voice-0.2.0.zip"
                 length="12345678" type="application/octet-stream"/>
    </item>
  </channel>
</rss>

No sparkle:edSignature attribute, by design. The enclosure URL is version-pinned; only the feed URL uses the latest redirect.

Known risks and how each is checked

  • Sparkle binary framework via SwiftPM in an executable target: verified in M1 by a local Developer ID build before any CI work.
  • Hardened runtime breaking mic capture or CGEvent typing: caught in M1 by running the hand-signed build.
  • Notarization rejecting nested Sparkle code: caught in M2 by reading the notarytool log on first failure.
  • macos-26 runner image availability: checked when writing release.yml; fallback is macos-15 with Xcode 26 selected.
  • Not covered: Homebrew cask, DMG, or a nightly channel. Say so if you want any of them later.
